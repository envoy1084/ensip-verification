# Lifecycle and Results

Verification is an evaluation of live inputs. A previous positive result is not
permanent protocol state.

## Checked-At Time

One `checkedAt` Unix time in whole seconds MUST be used for all wall-clock
checks in an attempt. Implementations MUST obtain or inject it independently of
the proof and MUST NOT replace it with the ENS block timestamp.

Immediately before returning a positive result, require:

```text
issuedAt <= checkedAt + 300
issuedAt < validUntil
checkedAt < validUntil
validUntil - issuedAt <= methodMaxLifetime
```

The 300-second allowance applies only to a claim issued slightly in the future.
It does not extend `validUntil`, an authority expiry, or method evidence.

| Method                        | `methodMaxLifetime`           |
| ----------------------------- | ----------------------------- |
| `https-origin.v1`             | 31,536,000 seconds            |
| `dns-txt.v1`                  | 31,536,000 seconds            |
| `account-signature.eip155.v1` | 7,776,000 seconds; not frozen |

All inequalities are exact. At `checkedAt == validUntil`, the claim is
expired.

## Effective Validity

Calculate:

```text
effectiveValidUntil = min(
  claim.validUntil,
  authorityValidUntil?,
  methodEvidenceValidUntil?
)
```

Missing optional values are omitted from the minimum. Before a positive result,
require:

```text
checkedAt < effectiveValidUntil
```

`effectiveValidUntil` is a hard upper bound, not a guarantee that the result
will remain positive. A record, descriptor, authority, signature policy, or
external publication can change earlier.

An ENS renewal observed by a later evaluation does not extend an earlier
result's `effectiveValidUntil`.

## Positive Cache Bound

A positive result MUST NOT be reused after:

```text
cacheUntil = min(
  checkedAt + 300,
  effectiveValidUntil,
  methodEvidenceCacheUntil?
)
```

The selected method defines `methodEvidenceCacheUntil` when authenticated
transport or live evidence provides a shorter reuse bound. Applications MAY
choose an earlier `cacheUntil`; they MUST NOT choose a later one.

Re-evaluation MUST obtain a fresh ENS snapshot and repeat every required live
check. A cached HTTP or DNS body may be reused only when its method permits it
and its authenticated freshness bound has not expired.

Negative-result caching and method-specific freshness calculations remain
unfrozen.

## Protocol Result

The minimal positive result is exactly:

```json
{
  "verified": true,
  "verificationType": "control"
}
```

All v0 methods defined by this reference return `control`. No v0 method
returns `attestation`.

When any required check is malformed, invalid, expired, unsupported,
unavailable, blocked by policy, or inconclusive, the protocol projection is:

```json
{ "verified": false }
```

This object is a semantic projection, not a required serialized wire format.
It applies only to the exact live record, ENS snapshot, external evidence, and
checked-at time used by the attempt.

## Diagnostics

An SDK MAY expose a detailed result in addition to the protocol projection.
Until diagnostic codes are frozen, they are implementation metadata.

At minimum, implementations SHOULD preserve the distinction between:

| Category       | Meaning                                                          |
| -------------- | ---------------------------------------------------------------- |
| Not configured | Target or descriptor is empty                                    |
| Unsupported    | A selected version, method, profile, or capability is absent     |
| Invalid        | A conclusive protocol, proof, or cryptographic check failed      |
| Expired        | A required exclusive time bound was reached                      |
| Unavailable    | A required RPC, network, DNS, or target service did not complete |
| Policy blocked | Local security policy forbids the required operation             |

No diagnostic category permits a positive protocol result. Implementations
MUST NOT turn unavailability into a cryptographic-invalidity claim.

## State Changes

Any of the following requires a fresh evaluation:

- target record or descriptor change;
- authority or relevant expiry change;
- resolver change, even when logical values may remain the same;
- authority code or ERC-1271 policy change;
- method publication, DNSSEC chain, target account, or revocation-state change;
- expiry or cache bound reached; or
- evaluation block removed by a reorganization.

An empty descriptor disables new positive evaluations but does not erase proof
copies. Restoring the previous live state may make an unexpired proof positive
again unless a future version adds an authoritative ownership or state
generation.

## Unfrozen v0 Parameters

Stable v0 conformance still requires:

- final account-method maximum lifetime;
- exact method evidence freshness calculations;
- ENS and target-chain maximum snapshot age;
- diagnostic codes and precedence;
- negative cache limits; and
- an explicit decision on reactivation of previously valid proof material.
