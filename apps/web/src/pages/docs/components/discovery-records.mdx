# Discovery Records

A verification descriptor is an ENS text record for one target record. Its key
is derived from the target record, so clients know where to find it.

```text
text("url") = "https://example.com/profile"
text("verification[text][url]") = "ensrv1 a=1 m=https-origin.v1 h=0x..."
```

## Key Mapping

| Target record    | Descriptor text key              | `recordType`  | `recordKey`       |
| ---------------- | -------------------------------- | ------------- | ----------------- |
| `text(key)`      | `verification[text][<key>]`      | `text`        | Exact key         |
| `addr(coinType)` | `verification[addr][<coinType>]` | `addr`        | Decimal coin type |
| `contenthash()`  | `verification[contenthash]`      | `contenthash` | Empty string      |
| `data(key)`      | `verification[data][<key>]`      | `data`        | Exact key         |

The resolver `node` argument is the same for both records and is omitted above.

For `text` and `data`, copy the key exactly. Do not trim, lowercase, normalize, or escape it. Brackets inside the key remain part of the key. example-

```text
text("agent-endpoint[mcp]")
→ text("verification[text][agent-endpoint[mcp]]")
```

For `addr`, encode the coin type as unsigned decimal. Use `60`, not `060` or `+60`. Bitcoin uses `0`.

## Resolution

For each verification attempt:

1. Normalize the ENS name using ENSIP-15.
2. Resolve the target record and descriptor through the Universal Resolver.
3. Use the same DNS-encoded name and Ethereum block for both reads.
4. Read ENS authority state at that same block.
5. Reject an empty target record or empty descriptor.

If the block is removed by a chain reorganization, run verification again. CCIP Read is allowed, but its callback must use the same pinned block.

## Issues And Decisions

<Accordion>
  <AccordionItem>
    <AccordionTitle>Why use one descriptor record per target record?</AccordionTitle>
    <AccordionContent>

A client usually starts with a record it already wants to verify. A deterministic
descriptor key lets it fetch that descriptor directly.

A single manifest would need to be rewritten whenever any record changes. It
would also complicate concurrent updates and per-record resolver permissions. A
future index may help with enumeration, but it must not be the source of truth.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>Why use `verification[type][key]`?</AccordionTitle>
    <AccordionContent>

The key mirrors the resolver selector. The record type prevents collisions
between different resolver functions, while the record key identifies the exact
record within that type.

For example, `text("60")` and `addr(60)` map to different descriptors:

```text
verification[text][60]
verification[addr][60]
```

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>Why use brackets instead of dots, colons, or hashes?</AccordionTitle>
    <AccordionContent>

Brackets keep the record type and record key visibly separate. Dots are already
common inside ENS text keys such as `com.github`, and hashes would make records
harder to inspect, edit, and debug.

Bracketed parameters also have precedent in draft ENSIP-25 and ENSIP-26 record
keys.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>Do brackets conflict with ENSIP-5 key rules?</AccordionTitle>
    <AccordionContent>

ENSIP-5 limits standardized global key names to lowercase letters, numbers, and
hyphens. This proposal therefore needs to explicitly register
`verification[...]` as a parameterized key family rather than treating it as an
ordinary ENSIP-5 global key.

This does not require a resolver change. Resolver text keys are arbitrary
strings, and existing ENSIP drafts already use bracketed parameters.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>What if a text key already contains brackets?</AccordionTitle>
    <AccordionContent>

Copy the target key exactly. Do not recursively parse its brackets.

```text
text("agent-endpoint[mcp]")
→ text("verification[text][agent-endpoint[mcp]]")
```

The verifier constructs the descriptor key from the known target selector. It
does not need to recover the target key by parsing the descriptor key.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>Why is the target key not normalized or escaped?</AccordionTitle>
    <AccordionContent>

Resolver keys are exact strings. Lowercasing, trimming, normalizing, or escaping
a key could point to a different record or make two distinct records share one
descriptor.

The verification key therefore contains the target key exactly as supplied to
the resolver.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>Why encode address coin types as decimal?</AccordionTitle>
    <AccordionContent>

One canonical representation prevents the same address record from having
several descriptor keys. For example, coin type 60 is always `60`, never `060`,
`+60`, or hexadecimal.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>Why resolve everything at the same block?</AccordionTitle>
    <AccordionContent>

The target record, descriptor, and ENS authority can change independently.
Reading them at different blocks could combine states that never existed
together.

Using one block gives the verifier one consistent ENS snapshot. If that block is
removed by a reorganization, the result is discarded and evaluated again.

    </AccordionContent>

  </AccordionItem>

  <AccordionItem>
    <AccordionTitle>Why use text records instead of a new resolver interface?</AccordionTitle>
    <AccordionContent>

Text records work with existing ENS resolvers and require no contract upgrade.
They also preserve per-key reads and permissions in resolvers that support them.

A new resolver interface would increase deployment and adoption requirements
without improving verification semantics.

    </AccordionContent>

  </AccordionItem>
</Accordion>
