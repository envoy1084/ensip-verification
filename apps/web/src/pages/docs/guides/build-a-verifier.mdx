# Build a Verifier

Implement the verifier as a deterministic pipeline. Keep ENS state reads,
untrusted proof parsing, authority selection, method processing, and client
policy in separate modules.

## Input And Output

```ts
type VerifyInput = {
  name: string;
  selector: RecordSelector;
  blockTag?: bigint | "safe" | "finalized";
};

type VerificationPolicy = {
  allowedMethods: ReadonlySet<string>;
  retrieval: "local-only" | "fetch-on-action" | "privacy-proxy" | "direct";
  maxPositiveCacheSeconds: number;
};
```

Return the result shape defined in [Results](../spec/results-and-errors). Keep
the live resolver value available independently of verification status.

## Modules

| Module     | Input                         | Output                                            |
| ---------- | ----------------------------- | ------------------------------------------------- |
| Name       | User string                   | Normalized name, DNS encoding, node               |
| Resolution | Name, selector, block         | Raw target bytes, descriptor bytes, block context |
| Descriptor | Descriptor bytes              | Authority version, method, URI, hash              |
| Envelope   | Proof bytes                   | Strict common claim, signatures, method object    |
| Authority  | Name, node, block, version    | Authority address and optional expiry             |
| Method     | Common context, method object | Canonical target, relationship, freshness         |
| Policy     | Method and retrieval request  | Permit, deny, or proxy decision                   |

## Pipeline

1. Normalize the name and derive the node.
2. Select an evaluation block and record its block hash and timestamp.
3. Resolve the target and verification records at that block.
4. Parse the descriptor and reject unsupported versions or methods.
5. Derive raw `valueHash` and the method target.
6. Apply retrieval policy before issuing a third-party request.
7. Retrieve and integrity-check the proof resource.
8. Parse the envelope with duplicate-member detection.
9. Compare every common claim field with locally derived values.
10. Validate claim lifetime.
11. Determine current exact-name authority at the evaluation block.
12. Validate `authoritySignature`.
13. Validate method-specific evidence.
14. Calculate `validUntil` and `cacheUntil`.
15. Confirm the evaluation block remains canonical when required by policy.
16. Return the relationship or the first applicable error.

Stages 6 and later may be reordered to avoid a request forbidden by policy.
Do not reorder a comparison in a way that changes observable error precedence.

## Parser Boundary

Treat descriptors, JSON, signatures, URLs, DNS data, and HTTP responses as
untrusted input.

Do not use `JSON.parse` as the first validation step because it discards
duplicate object members. Tokenize first, reject duplicates and resource-limit
violations, then construct objects.

Validate lexical form before semantic conversion:

- decimal strings before integer parsing;
- hexadecimal strings before byte decoding;
- descriptor fields before URI parsing;
- JSON object shape before EIP-712 encoding.

## Proof Retrieval

For HTTPS resources:

- validate every resolved connection address against SSRF policy;
- repeat validation after redirects and DNS changes;
- send no ambient credentials;
- validate platform WebPKI TLS;
- limit redirects to three unless the method forbids them;
- use 5-second connection and 10-second total timeouts;
- limit encoded and decoded bodies to 256 KiB;
- limit decompression to 20:1;
- stop reading immediately after a limit is exceeded.

`https-origin.v1` additionally forbids redirects. A browser CORS failure is a
retrieval failure, not cryptographic evidence that the proof is invalid.

## Snapshot Boundary

Pass the evaluation block explicitly to every Registry, Wrapper, Registrar, and
ERC-1271 call. Never allow an adapter to silently use `latest` after the target
record was read at another block.

For target-chain account signatures, record the target-chain block used for
ERC-1271 and apply client finality policy independently.

## Conformance

At minimum, test:

- valid and invalid descriptor grammar;
- duplicate JSON members;
- exact resolver-byte hashing;
- EIP-712 domain, struct hash, and digest;
- every Authority Algorithm 1 branch;
- URL, DNS, CAIP-10, EOA, and ERC-1271 method cases;
- expiry boundaries and reorganization handling;
- SSRF, redirect, timeout, and decompression failures;
- error precedence.

Use the machine-readable files listed under [Test Vectors](../reference/test-vectors).
