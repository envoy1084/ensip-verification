# Publish a Verification

## Initial Publication

1. Set or confirm the final target resolver value.
2. Resolve that value through canonical Universal Resolver.
3. Choose one concrete method supported by the selector.
4. Derive exact `recordType`, `recordKey`, raw `valueHash`, canonical target,
   Authority Algorithm 1, and method maximum lifetime.
5. Create the strict common claim.
6. Sign with current exact-name authority.
7. Obtain method evidence, including a target-chain signature when required.
8. Publish proof bytes at the method location or descriptor `u`.
9. If using `h`, hash decoded proof body bytes.
10. Verify the external publication independently.
11. Set the descriptor last.
12. Run final live verification.

Descriptor-last publication prevents clients from selecting a proof that is not
yet available.

## Descriptors

```text
ensrv1 a=1 m=https-origin.v1
ensrv1 a=1 m=authority-signature.v1 u=https://proofs.example/p/123
ensrv1 a=1 m=account-signature.eip155.v1 u=https://proofs.example/p/456 h=0x...
```

## Renewal

If proof location is stable:

1. create a new claim from current live value;
2. publish new proof bytes;
3. update descriptor `h` when present;
4. verify final live state.

For deterministic HTTPS publication, replace the proof at the stable
`proofKey` path. Caches remain bounded to 5 minutes.

## Record Rotation

When target value changes:

1. write final target record;
2. resolve final bytes;
3. create and publish proof for the new value;
4. update descriptor last when it contains `u` or `h`;
5. verify final state.

Intermediate states may return `none`; they must never return a false positive
because `valueHash` binds exact current bytes.

## Revocation

Delete or empty the verification descriptor for immediate ENS-side revocation.
Also remove live target publication when applicable. Cached positive results
expire at their bounded `cacheUntil`; high-trust clients revalidate immediately.
