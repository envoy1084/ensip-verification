# Method: `service-account.<provider>`

Service-account verification proves that a public service account or proof surface currently publishes a proof for an ENS resolver record.

The generic method `service-account` MUST NOT be used for production verification. Provider behavior differs too much across services. Production methods MUST be provider-scoped.

Examples:

```text
service-account.github
service-account.farcaster
service-account.lens
```

## Properties

| Property | Value |
| --- | --- |
| Method | `service-account.<provider>` |
| Kind | `control` |
| Freshness class | Provider-defined, usually `live-publication`. |
| `h` policy | Required for mutable proof URLs unless the provider profile defines an immutable proof surface. |

## Supported Records

Service-account methods usually verify text records.

Examples:

```text
text("com.github") = "alice"
text("com.twitter") = "alice"
text("com.discord") = "1234567890"
```

## Provider Profile Requirements

Each provider profile MUST define:

```text
stable account identifier
mutable handle behavior
username reuse behavior
proof publication surface
organization/account distinction
collaborator or write-access risk
proof revocation behavior
API or rate-limit dependency
canonical target string
allowed UI copy
```

If a provider exposes a stable account ID, the profile MUST bind to that stable ID. A mutable display handle alone SHOULD NOT be treated as stable identity.

## GitHub Example

Target text record:

```text
text("com.github") = "alice"
```

Verification descriptor:

```text
text("verification[text][com.github]") = "ensrv1 m=service-account.github u=https://gist.githubusercontent.com/.../proof.json h=0x..."
```

The GitHub provider profile must define whether the proof surface proves:

```text
user profile control
gist ownership
repository write access
organization control
```

These are not equivalent.

## Proof Envelope

```json
{
  "v": "ensrv1",
  "claim": {
    "name": "alice.eth",
    "node": "0x...",
    "recordType": "text",
    "recordKey": "com.github",
    "valueHash": "0x...",
    "method": "service-account.github",
    "target": "github:user:1234567",
    "authorityProfile": "ens-mainnet-v1",
    "validUntil": "1783209600",
    "nonce": "0x..."
  },
  "authoritySig": {
    "type": "eip712",
    "signature": "0x..."
  },
  "provider": {
    "handle": "alice",
    "stableId": "1234567",
    "proofSurface": "gist-revision"
  }
}
```

## Verifier Flow

1. Resolve the live text record.
2. Resolve the matching verification descriptor.
3. Require a provider-scoped method.
4. Fetch proof material according to provider profile and privacy mode.
5. Check `h` if required.
6. Resolve provider account metadata if the profile requires it.
7. Check stable account ID and handle semantics.
8. Check common claim fields and value hash.
9. Resolve current ENS authority and verify signature.
10. Check provider proof freshness and revocation.
11. Return `verified/control`.
