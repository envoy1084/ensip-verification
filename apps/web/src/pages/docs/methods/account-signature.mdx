# Account Signature Methods

:::warning[Work in progress]
This page has not been finalized. Requirements, formats, and examples may
change while the protocol is under discussion.
:::

Account-signature methods demonstrate control of the account represented by an
ENS address record. The target account signs evidence bound to the complete
common claim. The ENS authority independently signs the same common claim, so a
positive result requires approval from both sides of the association.

## Proof Locations

Address methods use one external proof source:

```text
# Content-addressed raw envelope
ensrv1 a=1 m=account-signature.bip322.v1 u=ipfs://bafk...

# HTTPS envelope
ensrv1 a=1 m=account-signature.eip155.v1 u=https://proofs.example/address.json
```

For IPFS, the CID MUST match the retrieved bytes. Version 1 accepts only a
pathless CIDv1 URI using lowercase base32, the `raw` codec, and `sha2-256`;
query and fragment components are forbidden. The raw block bytes are the
envelope bytes. For HTTPS, the signatures in the envelope authenticate the
claim; the URI only locates it.

`u` is required for both transports. Other URI schemes are forbidden.

For both account methods, `validUntil - issuedAt` MUST NOT exceed 90 days.

Version 1 defines only the EVM and Bitcoin profiles below. Future ENSIPs MAY add
new immutable account-signature methods for other CAIP namespaces and native
signature systems. A new method must define its coin-type mapping, canonical
target, exact signed bytes, proof encoding, account-to-key binding, and
deterministic validation rules.

## Method Selection

The concrete method identifier selects the complete verification procedure;
the proof only supplies evidence for that procedure. Version 1 therefore uses
`account-signature.eip155.v1` and `account-signature.bip322.v1`, not one generic
`account-signature.v1` with a proof-selected scheme. A proof-supplied scheme
would not be present in the signed common claim and would create invalid or
ambiguous namespace-and-algorithm combinations.

Method profiles MAY support multiple validation paths when the live account
state deterministically selects or validates them. They MUST NOT let an
untrusted proof field choose a weaker path. A future incompatible signing
procedure requires a new immutable method identifier.

## EVM: `account-signature.eip155.v1`

The method supports exactly 20-byte EVM address records. Coin types map to
EIP-155 chains as follows:

| ENS coin type                                             | EIP-155 chain ID |
| --------------------------------------------------------- | ---------------- |
| `60`                                                      | `1`              |
| `0x80000000 \| chainId`, for `1 <= chainId <= 0x7fffffff` | `chainId`        |

Other legacy SLIP-44 EVM coin types and coin type `0x80000000` are not
supported. The canonical target is a CAIP-10 identifier with a lowercase
40-digit hexadecimal address:

```text
eip155:<chainId>:0x<40-lowercase-hex>
```

The target signs:

```text
ENSRecordAccountProof(bytes32 commonClaimDigest,string account)
```

with this EIP-712 domain:

```text
name:              ENS Record Account Proof
version:           1
chainId:           target EIP-155 chain ID
verifyingContract: target account address
```

`proof` contains exactly:

```json
{
  "authoritySignature": "0x<signature>",
  "targetSignature": "0x<signature>"
}
```

Let `targetProofDigest` be the EIP-712 digest of the
`ENSRecordAccountProof` value and domain above. `targetSignature` is one opaque,
nonempty, `0x`-prefixed byte string and MUST NOT exceed 8,192 bytes. The proof
does not declare `eoa`, `contract`, or a signature algorithm. A verifier accepts
the target signature when either strict recovery from `targetProofDigest` of a
65-byte, low-`s`, `r || s || v` secp256k1 signature with `v` equal to 27 or 28
produces the target address, or ERC-1271 validation of
`(targetProofDigest, targetSignature)` against the target address returns
`0x1626ba7e`.

ERC-1271 is evaluated at one selected finalized target-chain block. That block
is part of the evaluation context and applies to the entire account check. The
verifier, rather than an untrusted proof field, selects and applies the allowed
validation paths. This supports EOAs, contract wallets, multisigs, and delegated
account implementations without creating an algorithm-confusion field.

An EVM proof does not include a public key: a valid EOA signature recovers the
address, while ERC-1271 binds opaque signature bytes directly to the target
contract.

## Bitcoin: `account-signature.bip322.v1`

The method supports Bitcoin coin type `0`. The resolver bytes MUST be a valid
ENSIP-9 Bitcoin scriptPubKey. The canonical target is:

```text
bitcoin:mainnet:<lowercase-scriptPubKey-hex>
```

The target signs the concatenation of ASCII `ENS Record Verification:`, one LF
byte (`0x0a`), and the lowercase `0x`-prefixed common claim digest. There is no
final LF or null terminator:

```text
ENS Record Verification:
0x<64-lowercase-hex-commonClaimDigest>
```

Version 1 accepts BIP-322 Simple for native P2WPKH, P2WSH without timelocks, and
P2TR without timelocks. The signature MUST use the `smp` variant prefix defined
by BIP-322 version 2.0.0, followed by canonical padded RFC 4648 base64 of the
consensus-serialized witness stack. Missing variant prefixes are rejected.
BIP-322's required script rules apply, including `SIGHASH_ALL`, or
`SIGHASH_DEFAULT` where BIP-322 permits it.

`proof` contains exactly:

```json
{
  "authoritySignature": "0x<signature>",
  "targetSignature": "smp<canonical-padded-base64-witness>"
}
```

The method identifier already selects BIP-322 Simple version 2, so the proof
does not repeat a freely selectable scheme or format. The verifier decodes
`targetSignature` and applies BIP-322 Simple verification to the live
scriptPubKey and exact message bytes. Other BIP-322 variants, legacy Bitcoin
message signatures, unsupported scripts, and incompatible sighash forms are
rejected.

## Result

After comparing the complete common claim and validating both the ENS-authority
signature and native target signature, return `verified: true` with
`verificationType: "control"`. Otherwise return `verified: false`.

## Security Boundary

The method demonstrates possession of credentials capable of satisfying the
target account at verification time. It does not prove that the account is
uncompromised, safe to pay, or legally owned by the ENS authority.
