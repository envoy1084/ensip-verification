# DNS TXT Method Profiles

## Purpose

The DNS TXT methods demonstrate control of a domain derived from an ENS record.
The domain must publish a matching proof hash in DNS, and DNSSEC must
authenticate the response. The proof remains bound to the exact live record
and current ENS authority. A successful check returns `verified/control`.

## Supported Records

| Method                      | Target resolver record      | Domain source          |
| --------------------------- | --------------------------- | ---------------------- |
| `dns-txt.url.v1`            | `text("url")`               | HTTPS URL host         |
| `dns-txt.email-domain.v1`   | `text("email")`             | Domain after final `@` |
| `dns-txt.https-endpoint.v1` | HTTPS `agent-endpoint[...]` | HTTPS URL host         |

URL profiles reject IP-address hosts. The email profile verifies only the
domain, not the mailbox or local part.

## Discovery Descriptor

The descriptor requires `u` and `h`:

```text
ensrv1 a=1 m=dns-txt.url.v1 u=https://proofs.example/alice-url.json h=0x<64-lowercase-hex>
```

## Publisher Flow

1. Resolve the live target resolver record.
2. Derive the lowercase ASCII DNS domain and claim target.
3. Construct the common claim with a lifetime no longer than 30 days.
4. Sign the claim with current ENS authority.
5. Publish the envelope at descriptor `u`.
6. Calculate `h` from the exact published body bytes.
7. Calculate `proofKey` and its DNS owner name.
8. Publish the TXT value in the derived DNS zone.
9. Set the verification descriptor in ENS.

## Proof Location

Descriptor `u` contains the common envelope. DNS publishes its hash.

Encode `proofKey` as lowercase, unpadded RFC 4648 base32 and query:

```text
<52-character-proof-key>._ens-record-verification.<ascii-domain> TXT
```

The protocol TXT RDATA is:

```text
ensrv1 h=<descriptor-h>
```

## Proof Payload

The resource at `u` is the common envelope with an empty `methodProof`:

```json
{
  "v": "ensrv1",
  "claim": {
    "name": "alice.eth",
    "node": "0x787192fc5378cc32aa956ddfdedbf26b24e8d78e40109add0eea2c1a012c3dec",
    "recordType": "text",
    "recordKey": "url",
    "valueHash": "0x34174bbdf078fba55709ff82e2d5929de2e915c964d18dc57907afc851781142",
    "authorityVersion": "1",
    "method": "dns-txt.url.v1",
    "target": "dns:example.com",
    "issuedAt": "1783728000",
    "validUntil": "1786320000"
  },
  "authoritySignature": "0x<65-byte-signature>",
  "methodProof": {}
}
```

## Verifier Flow

1. Resolve the live target resolver record and descriptor at one block.
2. Derive the ASCII domain and `dns:<domain>` target.
3. Calculate `proofKey` and the TXT owner.
4. Resolve the TXT RRset and validate its DNSSEC chain.
5. Require exactly one matching protocol RDATA.
6. Fetch descriptor `u` and require the body hash to equal `h`.
7. Parse and compare the common claim.
8. Resolve current ENS authority and validate its signature.
9. Require an empty `methodProof`.
10. Apply lifecycle and DNS freshness.

## Validation Rules

Concatenate character strings only within each TXT RDATA. A protocol RDATA is a
value beginning with `ensrv1 `. Ignore unrelated TXT RDATA. Reject multiple
protocol values.

Validate the answer and every CNAME or DNAME step to an accepted DNSSEC trust
anchor.

| Check                                                 | Failure                    |
| ----------------------------------------------------- | -------------------------- |
| Domain cannot be derived                              | `target_mismatch`          |
| `u` or `h` absent                                     | `invalid_descriptor`       |
| DNS transport unavailable                             | `proof_unavailable`        |
| DNSSEC unsigned, bogus, indeterminate, or unvalidated | `insecure_dns`             |
| Protocol TXT absent                                   | `proof_unavailable`        |
| Multiple protocol TXT values                          | `proof_invalid`            |
| TXT hash or proof body differs from `h`               | `proof_integrity_mismatch` |

## Result

Successful validation demonstrates control of `dns:<ascii-domain>` for the
exact live ENS record, returns `verified/control`, and reports
`dnssec: "validated"`.

## Cache And Lifecycle

Maximum claim lifetime is 30 days. `cacheUntil` uses the minimum validated TTL
across the answer and alias chain, capped at five minutes and by
`effectiveValidUntil`.

Deleting the TXT value or proof resource invalidates live method evidence after
the applicable cache period.

## Security Considerations

DNSSEC authenticates DNS data. It does not establish that a website, mailbox,
or endpoint is safe. The email profile does not verify mailbox access.

## UI Copy

Allowed:

- `Control of the DNSSEC-authenticated domain was demonstrated for this ENS record.`
- `The domain published a DNSSEC-authenticated proof for this ENS record.`

Forbidden:

- `Mailbox verified.`
- `Official domain.`
- `Safe domain.`

## Examples

URL record:

```text
text("url") = "https://example.com/profile"
text("verification[text][url]") = "ensrv1 a=1 m=dns-txt.url.v1 u=https://proofs.example/alice-url.json h=0x<64-lowercase-hex>"
target = dns:example.com
```

Email record:

```text
text("email") = "alice@example.com"
text("verification[text][email]") = "ensrv1 a=1 m=dns-txt.email-domain.v1 u=https://proofs.example/alice-email.json h=0x<64-lowercase-hex>"
target = dns:example.com
```
