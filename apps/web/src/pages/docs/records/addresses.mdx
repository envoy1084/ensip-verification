# Address Record Verification

An ENS address record contains chain-specific account bytes. Address
verification requires approval from the current ENS authority and a native
signature from the account represented by the exact live record.

## Records

EVM example:

```text
addr(60) = 0x1234567890abcdef1234567890abcdef12345678
text("verification[addr][60]") = "ensrv1 a=1 m=account-signature.eip155.v1 u=https://proofs.example/address.json h=0x<64-hex>"
```

Bitcoin example:

```text
addr(0) = <ENSIP-9 Bitcoin scriptPubKey bytes>
text("verification[addr][0]") = "ensrv1 a=1 m=account-signature.bip322.v1 u=ipfs://bafk..."
```

The coin type is part of the selector. A proof for `addr(60)` cannot verify
`addr(0)` or another address record.

## Bound Values

The common claim binds:

```text
name, node
recordType = addr
recordKey  = canonical decimal coin type
valueHash  = keccak256(exact resolver address bytes)
authority  = current exact-name ENS authority
method, canonical target, issuedAt, validUntil
```

The ENS authority signs the complete common claim. The target signs a
method-specific message that commits to the same common-claim digest. It does
not sign only the displayed address string.

## Publication Flow

```mermaid
sequenceDiagram
  participant P as Publisher
  participant ENS as ENS Resolver
  participant A as ENS Authority Contracts
  participant T as Target Account
  participant S as IPFS or HTTPS Proof Storage

  P->>ENS: Read exact addr bytes
  P->>A: Read current exact-name authority
  P->>P: Construct common claim and digest
  P->>A: Request EIP-712 authority signature
  A-->>P: Authority signature over common claim
  P->>T: Request native signature over method message
  T-->>P: EIP-712, ERC-1271, or BIP-322 proof
  P->>S: Publish proof envelope
  P->>ENS: Set verification descriptor
```

## Verification Flow

```mermaid
sequenceDiagram
  participant C as Client
  participant ENS as ENS Resolver
  participant A as ENS Authority Contracts
  participant S as Proof Storage
  participant T as Target Chain

  C->>ENS: Resolve addr and descriptor at block B
  ENS-->>C: Exact address bytes and descriptor
  C->>A: Resolve exact-name authority at block B
  A-->>C: Current authority
  C->>S: Fetch u and verify h or IPFS CID
  S-->>C: Proof envelope
  C->>C: Reconstruct and compare complete common claim
  C->>A: Validate authority signature at block B
  A-->>C: Authority approval valid
  C->>T: Validate native target signature
  T-->>C: Signature valid for live target
  C-->>C: verified true, verificationType control
```

The verifier performs these steps:

1. Resolve the exact address bytes and descriptor at one ENS block.
2. Hash the raw resolver bytes and derive the target for the selected coin type.
3. Determine current exact-name ENS authority at the same block.
4. Retrieve external `u` and apply its required hash or CID integrity check.
5. Reconstruct the expected common claim and compare every field.
6. Validate `authoritySignature` against the live ENS authority.
7. Construct the method-specific target-signature message.
8. Validate the EOA, ERC-1271, or BIP-322 proof against the live target account.
9. Require the proof to be within its validity interval.
10. Return `verified: true` with `verificationType: "control"`.

If any required step does not succeed, return `verified: false`.

## What The Result Means

A positive result demonstrates that the current ENS authority and credentials
controlling the target account both approved a claim bound to this exact live
ENS address record. It does not prove that they are the same person, that either
account is uncompromised, or that sending funds is safe.
