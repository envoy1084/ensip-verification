# Authority and Lifecycle

## Authority Algorithm 1

Descriptor `a=1` and signed `authorityVersion = 1` select this algorithm.
Unsupported versions return `unsupported_authority`; methods cannot override or
weaken the selected algorithm.

Ethereum mainnet constants:

```text
ENS Registry:    0x00000000000C2E074eC69A0dFb2997BA6C7d2e1e
Base Registrar: 0x57f1887a8BF19b14fC0dF6Fd9B2acc9Af147eA85
Name Wrapper:   0xD4416b13d2b3a9Bae7AcD5D6C2BbDBE25686401
```

At the evaluation block:

1. Read Registry owner for the exact node.
2. If Registry owner is Name Wrapper, read wrapper owner and exact-name expiry.
   Require a nonzero owner and `now < wrapperExpiry`. For a wrapped `.eth`
   second-level name only, also require the Base Registrar registration to be
   unexpired.
3. Otherwise, for an unwrapped `.eth` second-level name, use the unexpired Base
   Registrar registrant.
4. Otherwise, use Registry owner for the exact node.
5. Reject zero or indeterminate authority.

Do not accept resolver writers, profile managers, parent owners, Universal
Resolver operators, gateway signers, gateway owner fields, or indexers as exact
name authority.

## Subnames

Unwrapped Registry subnames do not automatically expire when a parent `.eth`
registration expires. Parent re-registration does not recursively delete child
Registry records. The new parent owner can replace the child, but until then the
existing exact child Registry owner remains authority.

Wrapped subnames have explicit expiry. The verifier rejects them at expiry even
if raw wrapper storage still contains an address.

Do not apply a `.eth` ancestor's registrar expiry to an exact wrapped subname.
An unexpired wrapped child can remain operational while its parent second-level
name is in registrar grace. The exact child's wrapper expiry is its bound.

This protocol verifies the exact name. It does not imply current parent
endorsement of an independently owned child.

Wildcard or offchain record resolution does not imply inherited authority. If
the exact name has no authenticated nonzero authority under Algorithm 1, return
`unsupported_authority` instead of falling back to a parent or gateway value.

## Validity Predicate

At evaluation time `now`, require:

```text
claim.issuedAt <= now + 300
claim.issuedAt < claim.validUntil
now < claim.validUntil
claim.validUntil - claim.issuedAt <= methodMaxLifetime
```

Then compute:

```text
effectiveValidUntil = min(
  claim.validUntil,
  authorityValidUntil,
  targetProofValidUntil,
  issuerValidUntil,
  methodValidUntil
)
```

Ignore inapplicable bounds. A positive result returns the effective bound, not
only the claim expiry.

## Invalidation

A previous positive result becomes invalid when any of the following occurs:

- target record is removed or its exact bytes change;
- descriptor is removed, emptied, or changed;
- descriptor `h` no longer matches selected proof bytes;
- exact-name authority changes or expires;
- method evidence disappears or changes for a live-publication method;
- target account signature no longer validates under required live account
  rules;
- issuer attestation expires or is revoked;
- any applicable validity bound is reached;
- the referenced ENS block is reorganized out.

Descriptor deletion is ENS-side revocation.

## Freshness Classes

| Class              | Rule                                                                                              |
| ------------------ | ------------------------------------------------------------------------------------------------- |
| `live-publication` | Current HTTPS, DNS, or provider publication is required. Removal revokes after bounded freshness. |
| `portable-signed`  | Pinned proof bytes may be reused while live ENS state and expiry remain valid.                    |
| `issuer-revocable` | Issuer trust and sufficiently fresh revocation status are required.                               |

## Caching

```text
cacheUntil = min(
  effectiveValidUntil,
  checkedAt + clientPositiveCacheMaxAge,
  liveEnsFreshUntil,
  proofFreshUntil,
  revocationFreshUntil
)
```

Recommended default positive cache maximum for passive display is 15 minutes.
Negative results should normally be cached for at most 5 minutes.

Payment routing, transaction approval, sign-in, account binding, and agent
connection MUST revalidate instead of using a passive-display result.
