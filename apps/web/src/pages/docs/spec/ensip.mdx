# ENSIP-X: ENS Resolver Record Verification

## Abstract

This ENSIP defines verification for individual ENS records. A name publishes a
second text record that selects a verification method. A verifier checks the
current ENS record, a signature from the current authority for the name, and the
proof required by that method.

The protocol uses existing ENS text records. It requires no resolver change or
new contract.

## Motivation

An ENS resolver answers questions such as:

```text
What is the url record for alice.eth?
```

It can return `https://example.com`, but that answer alone does not show that
`example.com` recognizes the ENS record. The same applies to an address record:
the resolver value alone does not show that the target account signed it.

This ENSIP lets a name publish instructions for checking one record. The proof
is tied to the current record value, so changing the record invalidates the old
proof.

A positive result describes the checks that passed. It does not establish that
the target is safe, official, legally owned, reputable, or non-malicious.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
"SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
"OPTIONAL" in this document are to be interpreted as described in RFC 2119 and
RFC 8174.

### Terminology

- **Target resolver record**: the existing ENS resolver record being evaluated.
- **Verification descriptor**: the value of the verification text record.
- **Method profile**: the algorithm that derives a target and validates
  method-specific evidence.
- **Common claim**: the EIP-712 claim shared by all method profiles.
- **Current ENS authority**: the account selected by the signed authority
  version for the exact name.
- **Live evaluation**: evaluation against the current target record,
  verification descriptor, authority, proof, and validity state.
- **Evaluation block**: the Ethereum block reference used for ENS and authority
  reads in one live evaluation.

The public status is `verified` or `none`. A positive result also identifies the
validated relationship:

- `authorization`: current ENS authority signed the exact live record;
- `control`: authorization plus evidence from the method target;
- `attestation`: authorization plus evidence from an issuer accepted by client
  policy.

### Discovery Records

Verification descriptors are stored in ENSIP-5 text records. Their keys follow
the target resolver record class.

| Target resolver call   | `recordType`  | `recordKey`                 | Verification text key            |
| ---------------------- | ------------- | --------------------------- | -------------------------------- |
| `text(node, key)`      | `text`        | Exact key                   | `verification[text][<key>]`      |
| `addr(node, coinType)` | `addr`        | Canonical decimal coin type | `verification[addr][<coinType>]` |
| `contenthash(node)`    | `contenthash` | Empty string                | `verification[contenthash]`      |
| `data(node, key)`      | `data`        | Exact key                   | `verification[data][<key>]`      |

For text and data records, clients MUST construct the verification key by exact
concatenation:

```text
"verification[text][" + key + "]"
"verification[data][" + key + "]"
```

The target key MUST be non-empty and MAY contain brackets. Clients MUST match
the fixed prefix and final `]`; they MUST NOT recursively parse brackets.

For address records, the coin type MUST be encoded as unsigned decimal without
a sign or leading zeroes, except that zero is encoded as `0`.

Clients MUST normalize names according to ENSIP-15. They MUST resolve the target
record and verification descriptor through the ENSIP-23 Universal Resolver for
the same exact DNS-encoded name and evaluation block. On Ethereum mainnet, the
Universal Resolver is:

```text
0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe
```

An empty target resolver value produces `none/record_missing`. An empty
verification descriptor produces `none/not_configured`.

### Verification Descriptor

The descriptor is an ASCII string:

```text
ensrv1 a=<authority-version> m=<method> [u=<uri>] [h=<hash>]
```

```text
descriptor  = "ensrv1" 1*(SP field)
field       = field-name "=" field-value
field-name  = 1*(%x61-7A / %x30-39 / "-")
field-value = 1*(%x21-7E)
```

Clients split each field on its first `=`.

| Field | Requirement                                                                            |
| ----- | -------------------------------------------------------------------------------------- |
| `a`   | Required exactly once. Canonical decimal `uint32` authority version.                   |
| `m`   | Required exactly once. Concrete method identifier matching `[a-z0-9][a-z0-9.-]{0,63}`. |
| `u`   | Method-defined absolute proof URI, maximum 1,024 bytes.                                |
| `h`   | Method-defined body hash: lowercase `0x` followed by 64 hexadecimal digits.            |

A descriptor MUST NOT exceed 2,048 bytes. Clients MUST reject non-ASCII input,
control characters, empty fields, duplicate fields, unknown fields, invalid
field values, and fields forbidden by the selected method profile.

Generators MUST emit one space between fields and field order `a`, `m`, `u`,
`h`. Field order is not semantically significant. Unknown descriptor versions,
authority versions, and methods fail closed.

When `h` is present, it is:

```text
keccak256(proofResourceBytes)
```

`proofResourceBytes` is the response body after HTTP transfer and content
decoding and before UTF-8 decoding or JSON parsing.

### Common Claim

Every method profile MUST use this exact EIP-712 type string:

```text
ENSRecordVerification(string name,bytes32 node,string recordType,string recordKey,bytes32 valueHash,uint32 authorityVersion,string method,string target,uint64 issuedAt,uint64 validUntil)
```

The type MUST NOT be extended, reordered, renamed, or partially signed.

| Field              | Requirement                                         |
| ------------------ | --------------------------------------------------- |
| `name`             | ENSIP-15 normalized exact name.                     |
| `node`             | `namehash(name)`.                                   |
| `recordType`       | Exact target resolver record type.                  |
| `recordKey`        | Exact key or canonical numeric parameter.           |
| `valueHash`        | Hash of the exact live resolver return bytes.       |
| `authorityVersion` | Numeric descriptor field `a`.                       |
| `method`           | Exact descriptor field `m`.                         |
| `target`           | Canonical target derived by the method profile.     |
| `issuedAt`         | Signer-asserted Unix time in seconds.               |
| `validUntil`       | First Unix timestamp at which the claim is invalid. |

The common proof envelope is:

```json
{
  "v": "ensrv1",
  "claim": {
    "name": "alice.eth",
    "node": "0x787192fc5378cc32aa956ddfdedbf26b24e8d78e40109add0eea2c1a012c3dec",
    "recordType": "text",
    "recordKey": "url",
    "valueHash": "0x34174bbdf078fba55709ff82e2d5929de2e915c964d18dc57907afc851781142",
    "authorityVersion": "1",
    "method": "https-origin.v1",
    "target": "https://example.com",
    "issuedAt": "1783728000",
    "validUntil": "1786320000"
  },
  "authoritySignature": "0x...",
  "methodProof": {}
}
```

The envelope and claim MUST be closed JSON objects. Clients MUST reject
duplicate members before constructing a map. Claim integers MUST be canonical
decimal strings in the range of their EIP-712 types. Byte values MUST use
lowercase, even-length, `0x`-prefixed hexadecimal.

The JSON serialization is not signed. Clients parse the claim fields and encode
them as EIP-712. `methodProof` MUST be a closed object defined by the selected
method profile.

### Value Hashing

The base protocol binds the exact live resolver value:

```text
valueHash = keccak256(valueBytes)
```

| Record type   | `valueBytes`                           |
| ------------- | -------------------------------------- |
| `text`        | Exact UTF-8 bytes returned by `text`.  |
| `addr`        | Exact binary bytes returned by `addr`. |
| `contenthash` | Exact bytes returned by `contenthash`. |
| `data`        | Exact bytes returned by `data`.        |

Method profiles MAY define semantic target canonicalization. They MUST NOT
change the base `valueHash` rule.

### Current ENS Authority

Descriptor `a=1` and claim `authorityVersion = 1` select Authority Algorithm 1
for ENS on Ethereum mainnet.

| Contract       | Address                                      |
| -------------- | -------------------------------------------- |
| ENS Registry   | `0x00000000000C2E074eC69A0dFb2997BA6C7d2e1e` |
| Base Registrar | `0x57f1887a8BF19b14fC0dF6Fd9B2acc9Af147eA85` |
| Name Wrapper   | `0xD4416b13d2b3a9Bae7AcD5D6C2BbDBE25686401`  |

Clients MUST apply the following procedure at the evaluation block:

1. Read `ENSRegistry.owner(node)` for the exact node.
2. If the Registry owner is the Name Wrapper:
   1. read the exact node with `NameWrapper.getData`;
   2. require a nonzero wrapped owner;
   3. require the evaluation block timestamp to precede wrapper expiry;
   4. select the wrapped owner and wrapper expiry;
   5. for a wrapped `.eth` second-level name, also require an unexpired Base
      Registrar registration and select the earlier expiry.
3. Otherwise, for an unwrapped `.eth` second-level name:
   1. compute `tokenId = uint256(keccak256(bytes(label)))`;
   2. read `BaseRegistrar.ownerOf(tokenId)` and `nameExpires(tokenId)`;
   3. require a nonzero registrant and unexpired registration;
   4. select the registrant and registrar expiry.
4. Otherwise, require and select the nonzero exact Registry owner.

Clients MUST NOT substitute an ancestor owner, resolver writer, wildcard
resolver, Universal Resolver, CCIP Read gateway, or gateway signer. If exact
authority cannot be authenticated, clients return `none/unsupported_authority`.

An unwrapped Registry subname does not inherit parent expiry. A wrapped subname
uses its own wrapper expiry. A wrapped `.eth` second-level name itself is also
bounded by Base Registrar expiry.

Authority Algorithm 1 uses this EIP-712 domain:

```text
name:              ENS Record Verification
version:           1
chainId:           1
verifyingContract: 0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe
```

For an EOA authority, clients MUST require a 65-byte secp256k1 signature with
canonical low `s`, `v` equal to 27 or 28, and recovery to the current ENS
authority. For a contract authority, clients MUST call ERC-1271 at the
evaluation block and require `0x1626ba7e`.

### Verification Lifecycle

Verification is a live evaluation. At local evaluation time `now`, clients MUST
require:

```text
issuedAt <= now + 300
issuedAt < validUntil
now < validUntil
validUntil - issuedAt <= methodMaxLifetime
```

`issuedAt` is signer-asserted and is not a trusted timestamp.

The result expiry is the earliest applicable expiry:

```text
effectiveValidUntil = min(
  claim.validUntil,
  authorityValidUntil?,
  methodProofValidUntil?,
  issuerAttestationValidUntil?
)
```

A positive result becomes invalid when the target resolver value changes, the
descriptor changes or is deleted, current ENS authority changes or expires,
method proof is removed or revoked, an applicable expiry is reached, or the
evaluation block is reorganized.

Descriptor deletion is ENS-side revocation. Resolver value changes invalidate
the proof through `valueHash`. Authority changes invalidate old signatures.

Clients MUST NOT reuse a cached positive result after `cacheUntil`:

```text
cacheUntil = min(
  effectiveValidUntil,
  live ENS freshness,
  method proof freshness,
  revocation freshness?,
  client cache policy
)
```

### Verification Results

A verifier returns `verified` only when all required common and method checks
pass. Otherwise it returns `none`.

A positive result contains:

| Field                     | Meaning                                      |
| ------------------------- | -------------------------------------------- |
| `status`                  | `verified`                                   |
| `relationship`            | `authorization`, `control`, or `attestation` |
| `method`                  | Validated concrete method identifier         |
| `name`, `node`            | Exact normalized name and node               |
| `recordType`, `recordKey` | Verified target selector                     |
| `target`                  | Method-derived canonical target              |
| `validUntil`              | `effectiveValidUntil`                        |
| `checkedAt`               | Evaluation time                              |
| `cacheUntil`              | Latest permitted cache reuse time            |

A non-positive result contains `status: none` and MAY include a stable error,
retry category, and diagnostic evidence. Verification failure MUST NOT hide,
modify, or invalidate the target resolver record.

### Method Profiles

A concrete method profile MUST define:

- immutable method identifier;
- positive relationship;
- supported target resolver records;
- descriptor `u` and `h` policy;
- canonical target derivation;
- proof location and payload;
- method-specific validation rules;
- binding to the complete common claim digest for additional signatures or
  attestations;
- maximum claim lifetime;
- proof freshness, expiry, revocation, and cache behavior;
- failure-to-error mapping;
- security considerations and permitted UI copy;
- conformance vectors.

The initial method registry is:

| Method                        | Relationship    | Primary records                      |
| ----------------------------- | --------------- | ------------------------------------ |
| `authority-signature.v1`      | `authorization` | Any supported target resolver record |
| `https-origin.v1`             | `control`       | HTTPS URL text records               |
| `dns-txt.url.v1`              | `control`       | `text("url")`                        |
| `dns-txt.email-domain.v1`     | `control`       | `text("email")`                      |
| `dns-txt.https-endpoint.v1`   | `control`       | HTTPS `agent-endpoint[...]` records  |
| `account-signature.eip155.v1` | `control`       | Supported EVM address records        |

Method-specific behavior is defined by the corresponding method profile. A
generic family name is not a valid descriptor method.

### Error Codes

When several checks fail, clients MUST return the first applicable error in this
table. Clients MAY reorder internal checks to enforce retrieval policy, but the
observable primary error MUST follow this precedence.

| Order | Error                         | Produced when                                               |
| ----: | ----------------------------- | ----------------------------------------------------------- |
|     1 | `invalid_request`             | Name or selector input is invalid.                          |
|     2 | `unsupported_record`          | Target selector is unsupported.                             |
|     3 | `resolution_unavailable`      | ENS or CCIP resolution is unavailable.                      |
|     4 | `record_missing`              | Target resolver record is empty.                            |
|     5 | `not_configured`              | Verification descriptor is empty.                           |
|     6 | `invalid_descriptor`          | Descriptor syntax or fields are invalid.                    |
|     7 | `unsupported_version`         | Descriptor or authority version is unsupported.             |
|     8 | `unsupported_method`          | Concrete method is unsupported.                             |
|     9 | `privacy_blocked`             | Client policy forbids required retrieval.                   |
|    10 | `proof_unavailable`           | Required proof cannot be retrieved.                         |
|    11 | `proof_integrity_mismatch`    | Proof resource bytes do not match descriptor `h`.           |
|    12 | `proof_invalid`               | Envelope or method proof is malformed.                      |
|    13 | `claim_mismatch`              | Name, node, selector, authority version, or method differs. |
|    14 | `value_mismatch`              | Live resolver value does not match `valueHash`.             |
|    15 | `target_mismatch`             | Method-derived target differs from the claim.               |
|    16 | `not_yet_valid`               | `issuedAt` exceeds the allowed clock skew.                  |
|    17 | `expired`                     | An applicable validity bound has been reached.              |
|    18 | `unsupported_authority`       | Current exact-name authority cannot be authenticated.       |
|    19 | `authority_signature_invalid` | Current ENS authority does not validate the signature.      |
|    20 | `target_proof_invalid`        | Method-specific target evidence does not validate.          |
|    21 | `insecure_dns`                | Required DNSSEC validation does not succeed.                |
|    22 | `revocation_unavailable`      | Required revocation status is unavailable.                  |
|    23 | `revoked`                     | Required status reports revocation.                         |
|    24 | `untrusted_issuer`            | Client policy rejects the attestation issuer.               |

### Example

Target resolver record:

```text
text("url") = "https://example.com/profile"
```

Verification descriptor:

```text
text("verification[text][url]") = "ensrv1 a=1 m=https-origin.v1"
```

Derived values:

```text
recordType = text
recordKey  = url
valueHash  = 0x34174bbdf078fba55709ff82e2d5929de2e915c964d18dc57907afc851781142
target     = https://example.com
proofKey   = 0x3e1afa3eb523cdefc3d8faa94c15e05fe1af4fb5096f71e127890e3763f5a380
```

The method profile defines the proof location:

```text
https://example.com/.well-known/ens-record-verification/3e1afa3eb523cdefc3d8faa94c15e05fe1af4fb5096f71e127890e3763f5a380
```

A verifier returns `verified/control` only after the live target value,
descriptor, common claim, current ENS authority signature, HTTPS publication,
and lifecycle checks all pass.

## Rationale

Verification keys follow existing ENS record types. A text record uses
`verification[text][...]`, an address uses `verification[addr][...]`, and a
contenthash uses `verification[contenthash]`. This avoids creating separate
categories for websites, wallets, profiles, and agents.

The ENS text record remains small. It selects the method and, when needed,
points to a proof. The signed claim and proof are stored outside ENS.

`valueHash` covers the exact resolver value. Methods interpret that value
separately. For example, the URL method derives an HTTPS origin while the
address method derives an account identifier.

Authority rules have their own version because ENS ownership rules can change
without changing record keys or proof methods.

The claim has no nonce. Verification already checks the current record,
verification record, ENS authority, method proof, and expiry. A nonce would not
add replay protection without a separate shared nonce registry.

## Backwards Compatibility

This ENSIP adds ENSIP-5 text records. Existing resolvers require no new
interface. Clients that do not implement this ENSIP ignore verification records
and continue to resolve target resolver records normally.

Missing, invalid, unsupported, expired, or unavailable verification has no
effect on the target resolver record.

## Security Considerations

A valid proof can bind an attacker-controlled ENS name to an attacker-controlled
target. Verification is not evidence of safety, reputation, legal ownership,
brand identity, or ENS endorsement.

Resolver write permission is not current ENS authority. Parent ownership is not
authority for an independently assigned child. Wildcard resolvers, Universal
Resolver, and CCIP Read gateways do not become verification authority.

Proof retrieval reveals lookup interest and processes attacker-controlled
network input. Method profiles and clients must define retrieval policy, TLS,
SSRF protection, DNS rebinding protection, redirect behavior, resource limits,
and parser limits.

A signature alone does not establish current verification. Clients must perform
a live evaluation of the target record, descriptor, current ENS authority,
method proof, expiry, and required revocation state.

User interfaces must identify the exact relationship and method. They must not
label a result as safe, official, trusted, non-malicious, legally owned, or
endorsed by ENS.
