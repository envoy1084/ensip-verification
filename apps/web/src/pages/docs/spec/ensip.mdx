# ENSIP-X: ENS Resolver Record Verification

## Abstract

This ENSIP defines record-scoped verification for ENS resolver records. A name
publishes a compact verification descriptor for a specific resolver record. A
verifier resolves the live record and descriptor through Universal Resolver,
binds the exact resolver bytes to one strict EIP-712 claim, verifies current
authority for the exact ENS name, and evaluates method-specific evidence.

The protocol supports three positive relationships:

- `authorization`: current ENS authority signed the exact live record value;
- `control`: authorization plus participation by the external target;
- `attestation`: authorization plus an issuer accepted by client policy.

The protocol requires no new contract. It uses existing ENS records, existing
authority contracts, ERC-1271, and offchain proof resources.

## Motivation

An ENS resolver proves what value it returns. It does not prove that current
exact-name authority explicitly authorized that value or that an external target
agrees with it.

Examples:

```text
text("url") = "https://example.com"
text("com.github") = "alice"
addr(60) = 0x1234...
contenthash() = ipfs://bafy...
```

These records do not by themselves prove control of the website, provider
account, target blockchain account, or content publisher. Resolver-writing
authority may also be delegated more broadly than name ownership.

This ENSIP answers only:

```text
For this exact ENS name, record selector, and live resolver value, did current
exact-name authority authorize the claim and did the selected method evidence
validate?
```

It does not define safety, reputation, legal ownership, brand authenticity,
anti-phishing status, or universal issuer trust.

## Specification

The key words MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT,
RECOMMENDED, NOT RECOMMENDED, MAY, and OPTIONAL are interpreted as described in
RFC 2119 and RFC 8174.

### Definitions

- **Target record**: existing ENS resolver record being evaluated.
- **Record selector**: resolver profile plus its key or parameter.
- **Verification record**: ENSIP-5 text record containing a descriptor.
- **Descriptor**: compact method and proof-discovery value.
- **Authority version**: versioned exact-name authority lookup algorithm.
- **Method**: immutable target-evidence algorithm.
- **Proof key**: stable record-method publication slot identifier.
- **Evaluation block**: one block reference used for every ENS read in an
  evaluation.
- **High-trust action**: payment, transaction approval, sign-in, account
  binding, agent connection, or equivalent security-sensitive action.

### Protocol Invariants

A verifier MUST NOT return `verified` unless:

1. target record and descriptor were resolved for the same normalized exact
   name and evaluation block;
2. descriptor is valid and selects supported authority and method versions;
3. claim binds normalized name, node, selector, exact live value hash,
   authority version, method, and canonical target;
4. current exact-name authority validates the authority signature;
5. selected method evidence validates;
6. all applicable validity, freshness, and revocation checks pass.

Verification failure MUST NOT invalidate or hide the target resolver record.

### Name Normalization

Input names MUST be normalized according to ENSIP-15 before DNS encoding,
namehash, resolution, signing, or comparison. Invalid names return
`invalid_request`.

The claim contains normalized Unicode `name`. The verifier recomputes
`node = namehash(name)` and requires equality with signed `node`.

### Universal Resolution

The target record and verification descriptor MUST be resolved through the
canonical ENSIP-23 Universal Resolver for the ENS deployment.

Ethereum mainnet canonical proxy:

```text
0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe
```

The two reads:

- use the same normalized DNS-encoded exact name;
- use the same evaluation block;
- SHOULD use one Universal Resolver smart multicall;
- process EIP-3668 callbacks under the same block context.

The returned resolver is diagnostic only. Resolver writers, delegates,
Universal Resolver operators, gateways, gateway signers, and
resolver-supplied owner values are not verification authority.

### Record Selectors And Verification Keys

Initial selectors:

| Target selector        | `recordType`  | `recordKey`                 | Verification text key            |
| ---------------------- | ------------- | --------------------------- | -------------------------------- |
| `text(node, key)`      | `text`        | Exact key                   | `verification[text][<key>]`      |
| `addr(node, coinType)` | `addr`        | Canonical decimal coin type | `verification[addr][<coinType>]` |
| `contenthash(node)`    | `contenthash` | Empty string                | `verification[contenthash]`      |
| `data(node, key)`      | `data`        | Exact key                   | `verification[data][<key>]`      |

Text and data verification keys are exact concatenation:

```text
"verification[text][" + key + "]"
"verification[data][" + key + "]"
```

Keys MUST be non-empty and MAY contain brackets. Parsers match the fixed prefix
and final `]`; they MUST NOT recursively parse brackets.

Coin type is unsigned decimal without a sign or leading zeroes except value
`0`.

The `data` namespace is reserved. A client without a concrete data method returns
`unsupported_record`.

Target records are missing when the resolver profile returns its defined empty
string or zero-length bytes.

### Descriptor

The verification record value is ASCII:

```text
ensrv1 a=<authority-version> m=<method> [u=<uri>] [h=<hash>]
```

ABNF:

```text
descriptor  = "ensrv1" 1*(SP field)
field       = field-name "=" field-value
field-name  = 1*(%x61-7A / %x30-39 / "-")
field-value = 1*(%x21-7E)
```

Fields:

| Field | Meaning                                                             |
| ----- | ------------------------------------------------------------------- |
| `a`   | Canonical unsigned decimal authority version. Required once.        |
| `m`   | Method identifier. Required once.                                   |
| `u`   | Absolute proof URI under method rules.                              |
| `h`   | Lowercase `0x` plus 64 hex digits containing body-byte `keccak256`. |

Method identifiers match:

```text
[a-z0-9][a-z0-9.-]{0,63}
```

Parser requirements:

- first token exactly `ensrv1`;
- descriptor at most 2,048 bytes;
- URI at most 1,024 ASCII bytes;
- reject duplicate, missing, empty, or unknown fields;
- reject unsupported authority version or method;
- reject malformed URI or hash;
- reject non-ASCII and control characters;
- accept field order but generators emit `a`, `m`, `u`, `h` order.

Unknown descriptor versions and fields fail closed. A verifier MUST NOT retry
using an older interpretation.

Each method declares `u` and `h` REQUIRED, PERMITTED, or FORBIDDEN.

### Strict Common Claim

Every proof uses exactly:

```solidity
ENSRecordVerification(
  string name,
  bytes32 node,
  string recordType,
  string recordKey,
  bytes32 valueHash,
  uint32 authorityVersion,
  string method,
  string target,
  uint64 issuedAt,
  uint64 validUntil
)
```

This type MUST NOT be extended, reordered, renamed, or partially signed.
Method-specific signed data uses a separate exact type that commits to the full
common claim digest.

Field requirements:

| Field                        | Requirement                                           |
| ---------------------------- | ----------------------------------------------------- |
| `name`                       | ENSIP-15 normalized exact name.                       |
| `node`                       | Recomputed namehash of `name`.                        |
| `recordType` and `recordKey` | Exact canonical selector.                             |
| `valueHash`                  | Exact live resolver-value hash.                       |
| `authorityVersion`           | Numeric descriptor `a`.                               |
| `method`                     | Exact descriptor `m`.                                 |
| `target`                     | Exact method-derived canonical target.                |
| `issuedAt`                   | Signer-asserted issuance time used to bound interval. |
| `validUntil`                 | First invalid Unix timestamp.                         |

### Raw Value Hashing

```text
valueHash = keccak256(valueBytes)
```

| Record type   | `valueBytes`                                      |
| ------------- | ------------------------------------------------- |
| `text`        | Exact UTF-8 bytes returned by resolver.           |
| `addr`        | Native binary address bytes returned by resolver. |
| `contenthash` | Raw contenthash bytes.                            |
| `data`        | Raw data bytes.                                   |

Method canonicalization MUST NOT replace exact value hashing.

### EIP-712 Domain

Ethereum mainnet version-one domain:

```text
name:              ENS Record Verification
version:           1
chainId:           1
verifyingContract: 0xeEeEEEeE14D718C2B47D9923Deab1335E144EeEe
```

The verifying contract is the long-lived Universal Resolver proxy used as
deployment domain separation. It does not execute signature verification.

### Authority Algorithm 1

Descriptor `a=1` and signed `authorityVersion = 1` select this algorithm.

Ethereum mainnet contracts:

```text
ENS Registry:    0x00000000000C2E074eC69A0dFb2997BA6C7d2e1e
Base Registrar: 0x57f1887a8BF19b14fC0dF6Fd9B2acc9Af147eA85
Name Wrapper:   0xD4416b13d2b3a9Bae7AcD5D6C2BbDBE25686401
```

At evaluation block:

1. Read Registry owner of exact node.
2. If Registry owner is Name Wrapper:
   - read exact node through `NameWrapper.getData`;
   - require nonzero wrapper owner and `now < wrapperExpiry`;
   - authority is exact wrapper owner;
   - authority expiry is wrapper expiry;
   - for a wrapped `.eth` second-level name only, require unexpired Base
     Registrar registration and use the earlier expiry.
3. Otherwise, if exact name is an unwrapped `.eth` second-level name:
   - require `BaseRegistrar.ownerOf(labelhash)` succeeds and is nonzero;
   - authority is registrant;
   - authority expiry is `nameExpires(labelhash)`.
4. Otherwise:
   - authority is Registry owner of exact node;
   - require nonzero owner;
   - no expiry exists unless exact ownership exposes one.

An ancestor owner MUST NOT replace a nonzero exact-name owner. Resolver
permissions do not confer authority. If exact authority cannot be authenticated,
including some virtual wildcard or offchain children, return
`unsupported_authority`; do not fall back to parent or gateway data.

#### Subnames

Unwrapped Registry subnames have no inherited expiry. Ancestor expiry,
transfer, or re-registration does not delete or transfer the exact child. The
exact child owner remains authority until it transfers the child or current
parent replaces it. Verification of a child does not imply parent endorsement.

Wrapped subnames use exact child wrapper expiry. Do not apply ancestor registrar
expiry to the child. Name Wrapper intentionally permits an unexpired child to
remain operational while its parent `.eth` second-level name is in registrar
grace. At child expiry, verification fails even if raw storage retains an
address.

#### Authority Signature

For EOA authority, require a 65-byte secp256k1 signature over common EIP-712
digest, canonical low `s`, and `v` 27 or 28.

For contract authority, call ERC-1271 at evaluation block with common digest and
signature bytes. Require exact magic value `0x1626ba7e`. Cap contract signature
bytes at 8 KiB.

Future authority semantics allocate a new numeric authority version. Existing
clients reject unsupported values. Methods MUST NOT override or weaken selected
authority algorithm.

### Proof Key

Define:

```solidity
PROOF_KEY_TYPEHASH = keccak256(
  "ENSRecordVerificationProofKey(bytes32 domainSeparator,uint32 authorityVersion,bytes32 node,bytes32 recordTypeHash,bytes32 recordKeyHash,bytes32 methodHash)"
);

proofKey = keccak256(
  abi.encode(
    PROOF_KEY_TYPEHASH,
    eip712DomainSeparator,
    authorityVersion,
    node,
    keccak256(bytes(recordType)),
    keccak256(bytes(recordKey)),
    keccak256(bytes(method))
  )
);
```

The key is stable across record changes and proof renewal but separated by ENS
deployment, authority algorithm, selector, and method.

### JSON Envelope

Common JSON envelope:

```json
{
  "v": "ensrv1",
  "claim": {},
  "authoritySignature": "0x...",
  "methodProof": {}
}
```

Requirements:

- valid UTF-8 without BOM;
- top-level object;
- exact common members shown above;
- reject duplicate members at every depth before map-based parsing;
- reject unknown members in envelope and claim;
- claim uint values encoded as canonical decimal strings and range checked;
- bytes encoded as lowercase, `0x`-prefixed, even-length hex;
- bytes32 exactly 32 bytes;
- maximum decoded envelope size 256 KiB;
- maximum JSON depth 16;
- maximum 128 members per object;
- maximum string length 8 KiB unless stricter field limit applies;
- `methodProof` validated by exact method schema.

JSON serialization is not signed. Parsed claim fields are encoded into the
strict EIP-712 type.

### Proof Resource Integrity

When descriptor `h` exists:

```text
keccak256(proofResourceBytes) == h
```

`proofResourceBytes` is body after transfer and content decoding, before UTF-8
or JSON parsing. Headers, chunk framing, and compressed transfer bytes are not
included.

`h` selects exact bytes; it is not a substitute for authority or method
signatures.

### Common Fetch Profile

Network proof retrieval MUST:

- use only method-permitted schemes; initial generic network URI scheme is
  HTTPS;
- reject loopback, private, link-local, multicast, reserved, documentation, and
  metadata-service addresses for IPv4 and IPv6;
- resolve and recheck every redirect target against SSRF policy;
- prevent DNS rebinding;
- send no ambient cookies, credentials, or authorization;
- validate TLS;
- allow at most 3 redirects unless method forbids redirects;
- allow at most 5 seconds connect time and 10 seconds total time;
- cap encoded body at 256 KiB and decoded body at 256 KiB;
- cap decompression ratio at 20:1;
- reject unsupported content encodings and invalid media type;
- cancel retrieval once a limit is exceeded.

Browser CORS failure is `proof_unavailable`, not invalid cryptographic evidence.

### Lifecycle

At evaluation time `now`, require:

```text
issuedAt <= now + 300
issuedAt < validUntil
now < validUntil
validUntil - issuedAt <= methodMaxLifetime
```

There is no expiration grace.

Effective expiry is the earliest applicable:

```text
effectiveValidUntil = min(
  claim.validUntil,
  authorityValidUntil,
  targetProofValidUntil,
  issuerValidUntil,
  methodValidUntil
)
```

A previous positive result becomes invalid after target value change,
descriptor deletion or change, authority transfer or expiry, method evidence
removal or invalidity, issuer revocation, effective expiry, or evaluation-block
reorganization.

Descriptor deletion is ENS-side revocation.

### Caching

```text
cacheUntil = min(
  effectiveValidUntil,
  checkedAt + methodPositiveCacheMaxAge,
  liveEnsFreshUntil,
  proofFreshUntil,
  revocationFreshUntil
)
```

Live publication methods cap positive caching at 5 minutes. `no-store` forces no
positive HTTP response cache. HTTP freshness and DNS TTL never extend method
cap. Network failures should not normally be cached; missing configuration or
proof may be cached for at most 5 minutes.

High-trust actions MUST perform fresh ENS and required live target or revocation
checks. An indexer result is only a hint.

### Privacy

Clients expose at least:

| Mode              | Behavior                                                           |
| ----------------- | ------------------------------------------------------------------ |
| `local-only`      | No third-party retrieval; return `privacy_blocked` when required.  |
| `fetch-on-action` | Retrieve only after explicit action or for a high-trust operation. |
| `privacy-proxy`   | Retrieve through a proxy that observes the lookup.                 |
| `direct-fetch`    | Retrieve directly after policy permits it.                         |

Passive profile rendering MUST NOT directly retrieve every external proof by
default. A client checks local method and issuer policy before making
issuer-controlled requests.

### Method Registry

Initial concrete methods:

| Method                        | Relationship    | Descriptor policy           | Max lifetime |
| ----------------------------- | --------------- | --------------------------- | ------------ |
| `authority-signature.v1`      | `authorization` | `u` required; `h` permitted | 90 days      |
| `https-origin.v1`             | `control`       | `u` and `h` forbidden       | 30 days      |
| `dns-txt.url.v1`              | `control`       | `u` and `h` required        | 30 days      |
| `dns-txt.email-domain.v1`     | `control`       | `u` and `h` required        | 30 days      |
| `dns-txt.https-endpoint.v1`   | `control`       | `u` and `h` required        | 30 days      |
| `account-signature.eip155.v1` | `control`       | `u` required; `h` permitted | 90 days      |

Method identifiers are immutable. Abstract names such as `service-account`,
`service-account.<provider>`, `issuer-attestation`, and
`issuer-attestation.<format>` are not valid concrete descriptor values.

Every concrete method specifies selector support, target derivation, descriptor
policy, proof schema, complete common-digest binding for signed or attested
method evidence, expiry, freshness, revocation, fetch policy, errors, UI
language, and vectors.

### Method: `authority-signature.v1`

- Supports any base record selector.
- `target` is empty.
- `methodProof` is empty.
- Descriptor requires `u`; `h` is permitted.
- Successful relationship is `authorization`.

It proves explicit current-authority approval, not external target control.

### Method: `https-origin.v1`

- Supports text records whose exact value parses as an absolute HTTPS URL under
  WHATWG URL parsing and its IDNA processing.
- Reject credentials, empty/opaque host, malformed URL, and invalid port.
- Target is serialized HTTPS origin with default port 443 omitted.
- Compute `proofKey`; encode as 64 lowercase hex characters without `0x`.
- Fetch without redirects or credentials:

```text
<origin>/.well-known/ens-record-verification/<proof-key-hex>
```

- Require status 200 and
  `application/ens-record-verification+json`.
- `methodProof` is empty; current same-origin publication is target evidence.
- Positive publication cache maximum is 5 minutes.

### DNS TXT Methods

Concrete methods:

```text
dns-txt.url.v1
dns-txt.email-domain.v1
dns-txt.https-endpoint.v1
```

Each derives one lowercase ASCII DNS domain from its record profile and sets
target `dns:<domain>`.

Encode `proofKey` as lowercase RFC 4648 base32 without padding. Query:

```text
<52-char-proof-key>._ens-record-verification.<domain> TXT
```

Exactly one protocol TXT RDATA after intra-RDATA string concatenation is
required:

```text
ensrv1 h=<descriptor-h>
```

The complete answer and alias chain MUST validate under DNSSEC to an accepted
trust anchor. Unsigned, bogus, indeterminate, or unvalidated DNS returns
`insecure_dns`. Use minimum validated TTL capped at 5 minutes.

Fetch descriptor `u`, require body hash equal `h`, validate empty
`methodProof`, then run common checks.

`email-domain` proves domain control only, not mailbox control.

### Method: `account-signature.eip155.v1`

Supported address records:

```text
coinType 60 -> eip155:1
coinType 0x80000000 | chainId -> eip155:<chainId>
where 1 <= chainId <= 0x7fffffff
```

Require exactly 20 address bytes. Canonical target:

```text
eip155:<base10-chain-id>:0x<40-lowercase-hex>
```

Coin type `0x80000000`, other legacy EVM SLIP-44 types, and non-EVM types are
unsupported by this method.

Target signs:

```solidity
ENSRecordAccountProof(bytes32 commonClaimDigest,string account)
```

under target-chain domain:

```text
name:              ENS Record Account Proof
version:           1
chainId:           CAIP-10 eip155 reference
verifyingContract: CAIP-10 target address
```

`methodProof` contains only `targetSignature`. EOA and ERC-1271 validation run
on the target chain. The target signature commits to full common claim digest.

## Rationale

### Why Per-record Discovery

Resolver-class keys identify the exact record without defining permanent product
categories such as URL, email, social, wallet, or agent. Existing resolvers work
without an upgrade.

### Why Universal Resolver

Universal Resolver is the stable record-resolution boundary across direct,
wildcard, and CCIP Read resolution. Authority remains separate because the
current Universal Resolver interface does not provide one authenticated
owner-and-expiry result for every exact name.

### Why A Signed Authority Version

Registry ownership can evolve while record selectors and target methods remain
stable. Signed `authorityVersion` isolates that evolution and makes old clients
fail closed rather than silently applying obsolete owner rules.

### Why Exact-name Authority

Resolver write permission is not equivalent to name ownership. Parent ownership
is not equivalent to ownership of an independently assigned child. Exact-name
authority prevents resolver delegates and parents from silently creating
stronger verification claims.

### Why Raw Value Hashing

URL, account, email, and content canonicalization differ. Exact raw hashing
preserves one common invariant while methods derive semantic targets separately.

### Why No Nonce

A nonce provides no replay prevention without a consumed-nonce or revocation
registry. Current descriptor, live value, current authority, method evidence,
and bounded signed interval already define validity. A future explicit
revocation identifier requires a new protocol version.

### Why Three Relationships

Authorization, target control, and issuer attestation answer different
questions. Treating owner-authorized contenthash as external control or an
issuer claim as direct control would overstate evidence.

## Backwards Compatibility

This ENSIP adds ENSIP-5 text records only. Unaware clients ignore them. Existing
target records remain canonical and continue to resolve normally.

Invalid, unsupported, missing, expired, or unavailable verification never makes
the target record invalid.

## Security Considerations

### No Safety Or Authenticity Claim

A valid proof can bind an attacker-controlled ENS name to an attacker-controlled
target. Verification is not anti-phishing, reputation, malware detection, legal
ownership, or brand authenticity.

### Exact-name Versus Parent Meaning

An exact child can remain owned after parent transfer or re-registration under
current ENS Registry semantics. Verification of the child does not mean the
current parent owner endorses it.

### Resolver And Gateway Separation

Record resolution may use a wildcard resolver or CCIP gateway. Neither becomes
verification authority. Exact authority failure returns
`unsupported_authority`.

### External Fetching

Proof retrieval leaks lookup interest and processes attacker-controlled network
input. Implementations enforce privacy defaults, SSRF restrictions, byte and
time limits, TLS, redirect rules, and parser limits.

### Stale Evidence

Clients recheck current descriptor, value, authority, target evidence, expiry,
and revocation. High-trust actions do not rely on passive cached results or
indexer assertions.

### UI Overclaiming

UI displays the exact relationship and method. It MUST NOT translate a result
into safe, official, trusted, legal owner, non-malicious, or ENS-endorsed.
