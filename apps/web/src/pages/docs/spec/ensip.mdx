# ENSIP-X: ENS Resolver Record Verification

## Abstract

This ENSIP defines record-scoped verification discovery for ENS resolver records. It allows an ENS name to advertise a compact verification descriptor for a specific resolver record and defines the common validation rules used by verification clients.

The ENSIP does not define product-specific verification namespaces such as `verification[url]`, `verification[social]`, or `verification[email]`. Verification follows resolver record classes:

```text
verification[text][<key>]
verification[addr][<coinType>]
verification[contenthash]
verification[data][<key>]
```

The base ENSIP defines discovery, descriptor parsing, value hashing, signed claims, current ENS authority, lifecycle, errors, and result semantics. Verification methods such as `https-origin`, `dns-txt`, `account-signature`, `service-account.<provider>`, `contenthash-binding`, and `issuer-attestation` are defined by separate method profiles.

## Motivation

ENS resolver records can point to resources outside ENS, including websites, service accounts, blockchain accounts, email addresses, content roots, issuer-backed claims, and agent endpoints. A resolver value proves what a resolver currently returns. It does not, by itself, prove that the current ENS authority controls the external target represented by that value.

This ENSIP standardizes a narrow verification question:

```text
For this ENS name and this exact resolver record value, is there a valid control proof or accepted attestation under the current ENS authority?
```

This ENSIP does not define a global trust system. A verified result does not mean that a URL is safe, an account is legitimate, an address is non-malicious, a content root is trustworthy, an issuer is globally trusted, or a resource is legally owned by the ENS name holder.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### Definitions

- **Target record**: the ENS resolver record being verified.
- **Verification record**: an ENSIP-5 text record whose key is defined by this ENSIP and whose value is a verification descriptor.
- **Verification descriptor**: the compact ASCII value stored in a verification record.
- **Method profile**: a specification that defines proof retrieval, target binding, external proof validation, result kind, freshness, and security considerations for a method identifier.
- **Current ENS authority**: the account recognized by the applicable authority profile as controlling the exact ENS name for record-verification purposes.
- **Control verification**: a positive result where the external target itself participates in the proof.
- **Attestation verification**: a positive result where an issuer asserts the binding and clients apply an explicit issuer trust policy.
- **Live evaluation**: verification performed against current ENS state, current resolver output, current descriptor state, current authority, and method-required proof freshness.

### Verification Record Keys

Verification records are ENSIP-5 text records. The key identifies the target resolver record. The value identifies the method used to verify the target record.

Initial verification keys are:

```text
verification[text][<text-key>]
verification[addr][<coinType>]
verification[contenthash]
verification[data][<data-key>]
```

`verification[data][<data-key>]` is reserved for resolvers that implement arbitrary byte-data records. Clients that do not support the target data resolver profile MUST return `none` with `unsupported_record`.

#### Text Records

For a target record resolved as:

```text
text(node, <text-key>)
```

clients MUST use:

```text
verification[text][<text-key>]
```

`<text-key>` is the exact ENSIP-5 text key. It MUST be non-empty. It MAY contain `[` or `]`.

The verification key is constructed by concatenation:

```text
"verification[text][" + textKey + "]"
```

Generic parsers MUST NOT use recursive bracket matching. To parse a text verification key, a client checks the prefix `verification[text][`, checks that the final character is `]`, and treats the substring between the prefix and the final `]` as `<text-key>`.

Examples:

| Target text key | Verification key |
| --- | --- |
| `url` | `verification[text][url]` |
| `email` | `verification[text][email]` |
| `com.github` | `verification[text][com.github]` |
| `agent-endpoint[mcp]` | `verification[text][agent-endpoint[mcp]]` |

#### Address Records

For a target record resolved as:

```text
addr(node, <coinType>)
```

clients MUST use:

```text
verification[addr][<coinType>]
```

`<coinType>` MUST be the decimal representation of the ENSIP-9 coin type. It MUST NOT contain a sign. It MUST NOT contain leading zeroes unless the value is exactly `0`.

Examples:

```text
verification[addr][60]
verification[addr][0]
verification[addr][501]
```

#### Contenthash Records

For a target record resolved as:

```text
contenthash(node)
```

clients MUST use:

```text
verification[contenthash]
```

No parameter is used.

#### Data Records

For a target record resolved as:

```text
data(node, <data-key>)
```

clients MUST use:

```text
verification[data][<data-key>]
```

`<data-key>` uses the same construction and parsing rules as `<text-key>`.

### Verification Descriptor

The verification record value is a compact ASCII descriptor. Full proof payloads MUST NOT be stored in the verification descriptor. JSON MUST NOT be used as the onchain descriptor format.

The descriptor format is:

```text
ensrv1 m=<method> [u=<uri>] [h=<hash>] [<extension-field>=<value> ...]
```

Examples:

```text
ensrv1 m=https-origin
ensrv1 m=dns-txt u=ipfs://bafy... h=0x5f3a...
ensrv1 m=account-signature u=ipfs://bafy... h=0xa8d2...
ensrv1 m=issuer-attestation u=https://issuer.example/proofs/4d8b... h=0x9e02...
```

#### Descriptor Grammar

```text
descriptor  = "ensrv1" 1*(SP field)
field       = field-name "=" field-value
field-name  = 1*(%x61-7A / %x30-39 / "-")
field-value = 1*(%x21-7E)
```

`field-value` MUST NOT contain spaces or control characters. Values that need spaces MUST use a method-defined encoding.

#### Descriptor Fields

| Field | Required | Meaning |
| --- | --- | --- |
| `m` | Yes | Method identifier. |
| `u` | No | Method-defined proof URI or pointer. |
| `h` | No | `keccak256` hash of the exact proof-resource bytes, encoded as lowercase `0x`-prefixed 32-byte hex. |

Rules:

- The first token MUST be exactly `ensrv1`.
- `m` MUST appear exactly once.
- A field name MUST NOT appear more than once.
- Unknown fields MUST be ignored after duplicate-field validation.
- An empty, missing, or invalid descriptor MUST NOT invalidate the target record; verification returns `none`.
- There is no `method=none`. Absence or an empty verification record means no proof is advertised.
- There is no `kind` descriptor field. The method profile determines whether a successful result is `control` or `attestation`.
- There is no descriptor-level expiry. Expiry is defined by the signed claim and method-specific proof material.

A descriptor advertises one method. Method profiles MAY define internal fallback behavior, but clients MUST NOT infer additional methods from a descriptor.

### Method Identifiers

A method identifier MUST match:

```text
[a-z0-9][a-z0-9.-]{0,63}
```

Method identifiers are immutable. Once a method identifier is published, its validation semantics MUST NOT be changed in a way that causes old proofs to be interpreted under different security assumptions. Incompatible changes MUST use a new method identifier.

Examples:

```text
https-origin
dns-txt
account-signature
contenthash-binding
issuer-attestation
service-account.github
https-origin.v2
```

Clients MUST return `none/unsupported_method` for unsupported method identifiers.

### Proof Resource Integrity

If the descriptor includes `h`, the verifier MUST compute:

```text
keccak256(exact proof-resource bytes)
```

and compare it to `h`. A mismatch MUST return `none/proof_integrity_mismatch`.

`h` is an integrity pin. It is not an expiry, trust policy, or revocation mechanism by itself. Each method profile MUST state whether `h` is ignored, optional, recommended, or required.

### Live Target Value and `valueHash`

A proof MUST bind to the exact live target resolver value. The base ENSIP defines raw value hashing only. Semantic normalization is method-specific and MUST NOT replace raw resolver-value binding.

The `valueHash` is computed as follows:

| Record type | Value hash input |
| --- | --- |
| `text` | UTF-8 bytes of the exact string returned by `text(node, key)` |
| `addr` | Native binary address bytes returned by `addr(node, coinType)` |
| `contenthash` | Raw bytes returned by `contenthash(node)` |
| `data` | Raw bytes returned by `data(node, key)` |

The hash is:

```text
valueHash = keccak256(valueBytes)
```

If the target resolver record is missing, malformed for its resolver profile, or hashes to a value different from the claim, verification MUST return `none`.

### Common Claim

Every method profile that uses an ENS-authority signature MUST sign the common claim below or a strict extension of it.

```solidity
struct ENSRecordVerification {
    string name;
    bytes32 node;
    string recordType;
    string recordKey;
    bytes32 valueHash;
    string method;
    string target;
    string authorityProfile;
    uint64 validUntil;
    bytes32 nonce;
}
```

Field meanings:

| Field | Meaning |
| --- | --- |
| `name` | Normalized ENS name. |
| `node` | Namehash of `name`. |
| `recordType` | `text`, `addr`, `contenthash`, `data`, or a registered future type. |
| `recordKey` | Text key, coin type string, data key, or empty string for `contenthash`. |
| `valueHash` | Hash of the exact live resolver value. |
| `method` | Method identifier from the descriptor. |
| `target` | Method-defined canonical external target. |
| `authorityProfile` | Authority profile used to determine the signer. |
| `validUntil` | First Unix timestamp at which the claim is invalid. |
| `nonce` | 32-byte replay-resistant value. |

The proof is valid only if:

```text
now < validUntil
```

### EIP-712 Domain

For `authorityProfile = ens-mainnet-v1`, the EIP-712 domain is:

```text
name:              "ENS Record Verification"
version:           "1"
chainId:           1
verifyingContract: 0x00000000000C2E074eC69A0dFb2997BA6C7d2e1e
```

Future authority profiles MUST define their own domain-separation rules.

### Current ENS Authority

A positive result requires a valid signature from the current ENS authority unless a method profile defines an equivalent or stronger authority check.

For `authorityProfile = ens-mainnet-v1`, the mainnet contract constants are:

```text
ENS Registry:    0x00000000000C2E074eC69A0dFb2997BA6C7d2e1e
Base Registrar: 0x57f1887a8BF19b14fC0dF6Fd9B2acc9Af147eA85
Name Wrapper:   0xD4416b13d2b3a9aBae7AcD5D6C2BbDBE25686401
```

For `authorityProfile = ens-mainnet-v1`:

1. Normalize the ENS name.
2. Compute `node = namehash(name)`.
3. Read `ENSRegistry.owner(node)`.
4. If the registry owner is the Name Wrapper contract and the wrapped owner is nonzero:
   - authority is `NameWrapper.ownerOf(uint256(node))`;
   - `authorityValidUntil` MUST NOT exceed wrapped-name expiry;
   - for wrapped `.eth` second-level names, `authorityValidUntil` MUST also not exceed Base Registrar registration expiry.
5. Else, if the name is an unwrapped `.eth` second-level name:
   - authority is `BaseRegistrar.ownerOf(uint256(labelhash(label)))`;
   - the Base Registrar registration MUST be unexpired;
   - `authorityValidUntil` MUST NOT exceed Base Registrar registration expiry.
6. Else:
   - authority is `ENSRegistry.owner(node)`.
7. If authority is the zero address or cannot be determined, verification MUST return `none/unsupported_authority`.
8. If authority is an EOA, the EIP-712 digest MUST recover to authority.
9. If authority is a contract, the verifier MUST call ERC-1271 `isValidSignature` on authority.

The verifier checks authority for the exact name being verified. Parent ownership does not automatically authorize a child name. Resolver writers, resolver delegates, approved operators, hosted profile managers, gateway signers, indexers, and unverified gateway `owner` fields MUST NOT be treated as current ENS authority under the base profile.

### Verification Algorithm

A verifier for a record MUST perform the following common checks in order:

1. Normalize the ENS name and compute `node`.
2. Validate `recordType` and `recordKey`.
3. Resolve the live target resolver record.
4. Compute `valueHash` from the live resolver value.
5. Resolve the verification text record key for the target record.
6. Parse the descriptor.
7. Select the method verifier named by `m`.
8. Fetch or read method-specific proof material according to the method profile and privacy mode.
9. If `h` is present, check proof-resource integrity.
10. Parse the proof envelope and common claim.
11. Check claim fields: `name`, `node`, `recordType`, `recordKey`, `method`, `authorityProfile`, and `valueHash`.
12. Derive and check the method-specific `target`.
13. Check expiry using the lifecycle rules.
14. Resolve current ENS authority.
15. Validate the ENS-authority signature.
16. Validate method-specific external control proof or issuer attestation.
17. Check revocation if required by the method profile.
18. Return `verified` only if every required check succeeds.

### Lifecycle and Revocation

Verification is a live evaluation, not a permanent credential.

A positive result at time `T` requires all of the following:

```text
live target record still matches
live verification descriptor still selects the method/proof
current ENS authority still verifies the signature
method-specific target proof or attestation verifies
required revocation checks pass
T is before every applicable expiry
```

The effective validity bound is:

```text
effectiveValidUntil = min(
  claim.validUntil,
  authorityValidUntil,
  targetProofValidUntil,
  issuerAttestationValidUntil,
  methodValidUntil
)
```

Inapplicable bounds are ignored. A positive result MUST return `validUntil = effectiveValidUntil`.

The following events MUST invalidate a previously positive result:

- target resolver record removal;
- target resolver value change;
- verification descriptor removal;
- verification descriptor method change;
- required descriptor `u` change;
- descriptor `h` mismatch;
- ENS authority change;
- ENS name expiry;
- wrapped-name expiry;
- external proof removal or mismatch for live-publication methods;
- issuer revocation for issuer-revocable methods;
- any applicable expiry reaching `now`.

Descriptor deletion is sufficient ENS-side revocation. If the verification descriptor is absent, empty, invalid, or no longer selects the proof method, clients MUST NOT return `verified` for an old proof.

### Proof Freshness Classes

Each method profile MUST declare one proof freshness class:

| Class | Meaning |
| --- | --- |
| `live-publication` | Current publication at the target proof surface is required. Removal or change revokes the proof. |
| `portable-signed` | Cached proof bytes may be reused if integrity and all live ENS checks pass. Revocation is primarily expiry or method-defined. |
| `issuer-revocable` | Issuer signature, trust policy, and revocation status are required. |
| method-defined | The method profile defines a stricter hybrid. |

### Caching

Cached positive results MUST NOT be reused after:

```text
cacheUntil = min(
  effectiveValidUntil,
  checkedAt + clientPositiveCacheMaxAge,
  liveEnsFreshUntil,
  proofFreshUntil,
  revocationFreshUntil
)
```

A client MUST revalidate before high-trust actions such as payment routing, transaction approval, sign-in, account binding, agent connection, or security-sensitive display.

HTTP cache headers and DNS TTLs are freshness hints only. They MUST NOT extend validity beyond `effectiveValidUntil`.

### Verification Result

A verifier returns either `verified` or `none`.

```ts
type VerificationResult =
  | {
      status: "verified";
      kind: "control" | "attestation";
      method: string;
      name: string;
      node: `0x${string}`;
      recordType: string;
      recordKey: string;
      target: string;
      validUntil: number;
      checkedAt: number;
      cacheUntil: number;
      assurance?: VerificationAssurance;
      issuer?: IssuerMetadata;
    }
  | {
      status: "none";
      error?: VerificationError;
      checkedAt?: number;
    };
```

Optional assurance metadata MUST NOT create additional public verification states.

```ts
type VerificationAssurance = {
  dnssec?: boolean;
  proofIntegrity?: "none" | "hash-pinned" | "content-addressed";
  publication?: "live" | "portable" | "issuer-revocable";
  authority?: "eoa" | "erc1271";
};
```

### Error Codes and Precedence

Clients MUST use the following common error precedence when multiple failures apply:

| Order | Error | Condition |
| ---: | --- | --- |
| 1 | `invalid_request` | Invalid input name, record type, record key, or coin type. |
| 2 | `unsupported_record` | Record type or resolver profile is unsupported. |
| 3 | `record_missing` | Live target resolver record is absent. |
| 4 | `not_configured` | Verification descriptor is absent or empty. |
| 5 | `invalid_descriptor` | Descriptor cannot be parsed or contains duplicate fields. |
| 6 | `unsupported_method` | Descriptor method is unknown or unsupported. |
| 7 | `privacy_blocked` | Client policy forbids required external proof fetching. |
| 8 | `proof_unavailable` | Proof resource cannot be fetched or read. |
| 9 | `proof_integrity_mismatch` | Descriptor `h` does not match proof bytes. |
| 10 | `proof_invalid` | Proof envelope or method payload is malformed. |
| 11 | `claim_mismatch` | Claim name, node, record type, record key, authority profile, or method does not match. |
| 12 | `value_mismatch` | Claim `valueHash` does not match the live resolver value. |
| 13 | `target_mismatch` | Claim target does not match the method-derived target. |
| 14 | `expired` | Claim, authority, proof, issuer, or method expiry has passed. |
| 15 | `unsupported_authority` | Current ENS authority cannot be determined. |
| 16 | `signature_invalid` | ENS authority signature does not verify. |
| 17 | `revoked` | Required revocation check reports revoked. |
| 18 | `untrusted_issuer` | Issuer proof is cryptographically valid but not accepted by client policy. |

Method profiles MAY define internal errors but MUST map them into the common set.

### Proof JSON Envelope

Method profiles MAY use JSON proof envelopes. JSON proof envelopes MUST follow these rules:

- bytes MUST be UTF-8 encoded JSON;
- the top-level value MUST be an object;
- duplicate object member names at any object level MUST invalidate the proof before schema validation;
- bytes32 values MUST be lowercase `0x`-prefixed 32-byte hex strings;
- byte strings MUST be lowercase `0x`-prefixed even-length hex strings;
- integer values that feed signatures SHOULD be encoded as decimal strings in JSON and converted before signing or verification;
- unknown fields in common objects MUST be ignored unless the method profile says otherwise.

The JSON envelope itself is not signed as JSON bytes unless a method profile explicitly says so. The common claim is signed as typed structured data.

### Privacy Modes

Verification may require external requests. Clients SHOULD expose at least the following fetch modes:

| Mode | Behavior |
| --- | --- |
| `local-only` | Do not fetch external proof resources. Return `none/privacy_blocked` when external proof fetching is required. |
| `fetch-on-action` | Fetch external proof resources only after user action or before a high-trust action. |
| `privacy-proxy` | Fetch through a proxy or cache that reduces direct user-to-target leakage. |
| `direct-fetch` | Fetch proof resources directly. |

Passive profile rendering SHOULD NOT fetch all advertised proofs directly by default.

### Method Profile Requirements

Every method profile MUST define:

- method identifier;
- result kind: `control` or `attestation`;
- supported record types and keys;
- target derivation;
- proof freshness class;
- descriptor field requirements;
- proof location or proof resource rules;
- proof payload format;
- `h` policy;
- expiry sources;
- revocation requirements;
- cache and freshness caps;
- error mappings;
- privacy considerations;
- allowed and forbidden UI language;
- test vectors.

## Rationale

The discovery key follows ENS resolver record classes because the target being verified is an ENS resolver record, not a product category. This avoids a permanent taxonomy of `url`, `social`, `email`, `wallet`, `agent`, and future categories.

The descriptor is compact because ENS text record storage is expensive relative to offchain proof publication. The descriptor selects a method and, when needed, a proof pointer. Full proof data belongs offchain.

The base ENSIP uses raw resolver-value hashing to avoid method-specific normalization in the common layer. URLs, email addresses, social handles, and chain accounts all have different normalization rules. Method profiles can define semantic targets, but the proof must still bind to the exact live resolver value.

The public result model is intentionally small. `verified` means that a supported method produced a valid proof under current state. `none` means no supported valid proof was found. Additional information is returned as metadata, errors, or debug output.

## Backwards Compatibility

This ENSIP does not change existing resolver interfaces. Existing clients that do not know this ENSIP will ignore the new verification text records and continue to display resolver records as before.

Existing ENS records are not invalidated by absent, invalid, or unsupported verification descriptors. Verification failure affects only the verification result for the target record.

## Security Considerations

### Verified Does Not Mean Safe

A positive result does not imply safety, legal ownership, endorsement, authenticity, anti-phishing status, or issuer trust outside the client's policy.

### Stale Records

Resolver records may survive name transfer, wrapper transfer, resolver migration, or name expiry. Clients MUST evaluate current ENS authority and live resolver state before returning `verified`.

### Resolver Writers Are Not Authority

The ability to edit a resolver record is not the same as authority to make verification claims for an ENS name. Resolver delegates, profile managers, gateway signers, and hosted tools MUST NOT be accepted as current ENS authority under the base profile.

### External Fetch Privacy

Fetching proof resources can leak interest in an ENS name and record. Wallets SHOULD avoid automatic direct fetching in passive views and SHOULD use privacy-preserving modes where appropriate.

### DNS Assurance

Unsigned DNS TXT verification depends on ordinary DNS resolution. DNSSEC-backed proofs MAY provide stronger assurance metadata, but they MUST NOT create a separate public status.

### Contenthash Binding

A contenthash binding proof verifies intentional binding between an ENS name and a content root. It does not prove that content is safe, official, current, or controlled by a mutable publisher account.

### Issuer Attestations

Issuer attestations are policy-bound. A cryptographically valid issuer attestation MUST NOT be treated as trusted unless the client explicitly trusts the issuer under a policy.

### JSON Parsing

JSON proof parsers MUST reject duplicate member names before schema validation. Implementations MUST NOT rely on JSON Schema alone for this property.
